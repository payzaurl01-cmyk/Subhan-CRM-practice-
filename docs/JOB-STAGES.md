# Conditional job workflow — 22 October 2026

Implementation and automated checks are local. The new database extension, frontend and targeted existing-job corrections have not been deployed/applied. The issue is **not yet verified as fixed on the live CRM**. No live jobs, tasks, stock, accounts or financial records were changed. Supabase inspection was read-only.

## Root cause

The visible CRM stored `job.status` and `task.jobStage`, but `nextJobStage` always selected the full picking/collection/installation chain. Quotation conversion conditionally created picking tasks, then unconditionally attached scheduling to `Collected` and generated installation work/evidence regardless of service type. Some guards used `items.length` instead of actual stock requirements. Admin status overrides could bypass task checks. The deployed normalized `accept_quotation_and_create_job(uuid)` separately created warehouse work/pick lists even for quotations without inventory.

There was no independent manual job-creation screen or per-job stage editor to recover; this change adds those controls inside the existing Jobs screen, using the same job/task records. Existing job/site editing, picking/returns, product-request, billing, approval and Master Control interfaces remain.

## Behavior

- Company-stock requirements use physical line kind, explicit inventory flags, fulfilment source, active/cancelled state, positive required quantity and previously issued quantity. Labour, service/custom charges, zero/cancelled lines and customer-supplied goods do not create stock steps. Fully issued quantities do not generate another issue cycle.
- Default installation: Confirmed → Installation Scheduled → Installation in Progress → Completed. Default repair uses Repair Scheduled / Repair in Progress. Supply-only omits field-work stages. Outstanding company stock adds Picking → Ready for Collection → Collected; actual unavailability adds Stock Shortage. Actual unresolved returns add Return Pending.
- Per-job stages extend `job.stages`; current status and task links retain their existing identifiers. Generated/manual provenance, applicability, system type, ordering, description, evidence/stock conditions and completion history persist in the existing JSON records. Manual labels retain their system validation type. Completed stages/tasks are preserved. Not-applicable work is excluded from requirements and progress.
- Scheduling can happen ahead of collection. New stock added during ongoing work preserves the active work stage and completed work; management can select which outstanding tasks depend on the added line. Final completion remains blocked by outstanding stock, returns, mandatory tasks and after evidence. Fresh required work gets a new evidence task instead of resetting the completed evidence task.
- Admin/Manager/Super Admin controls require current effective `jobs.create` or `jobs.update`, as applicable. Manual task creation also requires `tasks.create`. Structural editing is denied to installers, even if they can update assigned work. Overrides are consumed through the existing backend resolver; no grants are reset.
- Product forms support add/variant/quantity changes, exclusion and company/customer source. They require an explicit variation-price confirmation and reason. Variations feed existing final billing reconciliation. Accepted quote totals, issued invoices, payments and historical settlements remain unchanged; issued-return credits are not credited a second time as quantity variations.
- Reserved/unissued quantity reductions use exact normalized job/item/balance mappings, row locks and transactional release of only the affected quantity, including pick-line adjustment. On-hand stock, movement history and collection records are not rewritten. Issued/consumed goods require their actual return/correction path before reduction; a cancellation cannot erase the obligation.
- The existing job editor adds separate postcode and exact site-coordinate fields plus an explicit outstanding-task transfer confirmation/reason. Completed task assignees and evidence coordinates stay intact. Backend checks restrict editing, validate the installer/site coordinates, and transfer only outstanding applicable tasks. Notifications go to affected assignees; task completion alerts use authorized management recipients. Stable IDs avoid retry duplicates.
- Before photo/video evidence does not request GPS. After uploads save the file/reference first, then capture the uploading installer's device coordinates. GPS denial retains uploaded media/reference and offers Retry evidence location. Completion is confirmed only after saved metadata/location and task completion; job/address coordinates are never substituted.
- Completion remains Completed + Pending Approval. Existing review RPCs are reused. Explicit reopening preserves completion/approval history, adds a new outstanding work occurrence/evidence requirement and requires fresh completion/review. The existing approval fingerprint includes stages/work type/reopening, and its validation ignores not-applicable tasks.

## Backend and files

`supabase/migrations/20261022141817_conditional_job_workflow.sql` is a focused pending extension. It adds an RLS-protected idempotency receipt table, private workflow/validation/reconciliation helpers, `crm_job_workflow_command` and an authorized correction preview. Commands lock the job, check its expected revision, validate effective permissions and commit job/tasks, reservation changes, audit, notifications and receipt together. Repeated operation IDs cannot release or insert twice; changed payloads are rejected, and replay returns a current locked snapshot. Direct CRM writes also encounter management, immutable-history, stock-counter, evidence and completion guards.

The inspected normalized quotation function is updated with a baseline definition guard; its original signature and grants remain. A compatible two-argument overload accepts an explicit work type. `job_orders.work_type` and `applicable_stages` are additive fields because that normalized schema had no repair/supply discriminator. No tables/functions are dropped or recreated, and no business-data reset runs.

The extension requires the already prepared Master Control effective-identity migration. It does not deploy the older inventory or approval proposals. If the approval functions are already installed, compatible targeted updates extend their existing guards/fingerprint; otherwise the separate documented approval release is still required.
